**Volt is a stackful coroutine runtime for Zig.** Code reads like
blocking I/O. There is no `async`/`await`, no `Future` state machine,
no `.poll()`, no manual `Pin`. Each task owns a growable virtual stack;
the runtime suspends at every I/O, channel, sleep, or sync wait point
and resumes on whichever worker the reactor wakes first.

```zig
const std = @import("std");
const volt = @import("volt");

pub fn main() !void {
    var rt = try volt.Runtime.init(.{ .allocator = std.heap.smp_allocator });
    defer rt.deinit();
    try (try rt.run(echoServer, .{}));
}

fn echoServer() !void {
    var listener = try volt.net.TcpListener.bind(.any4(8080));
    defer listener.close();
    while (true) {
        const conn = try listener.accept();
        _ = try volt.spawn(echoOne, .{conn});
    }
}

fn echoOne(conn: volt.net.TcpStream) void {
    var s = conn;
    defer s.close();
    var buf: [4096]u8 = undefined;
    while (true) {
        const n = s.read(&buf) catch return;
        if (n == 0) return;
        s.writeAll(buf[0..n]) catch return;
    }
}
```

That's the whole shape. `s.read(&buf)` suspends the coroutine when the
socket isn't ready and resumes it when the reactor (kqueue / epoll /
io_uring / IOCP, depending on platform) delivers readiness — possibly
on a different worker thread.

## Status

This is **v1.0.0-zig0.16.0**, tagged for Zig 0.16. The runtime works
for what it claims — see the [bench gate](/performance/) — but
several pieces are still in flight.

| Target | Status |
|---|---|
| Darwin arm64 (kqueue) | **Working** — primary dev platform; full bench suite green |
| Linux arm64 (epoll) | **Working** — cross-compile + epoll-specific tests green; runtime CI pass pending |
| Linux arm64 (io_uring, poll mode) | **Working** — kernel ≥ 5.10 via `Runtime.Config.io_backend = .io_uring` |
| Windows arm64 (IOCP, readiness polyfill) | **Cross-compiles cleanly** — runtime validation deferred to a Windows VM/CI pass |
| x86_64 (Linux + Windows) | Cross-compile only — needs an x86_64 ctx switch (#149) |
| Cancellation | **Shipping** — `Cancel`, cancel-aware variants, `scope` |
| File I/O / DNS / TLS / HTTP | Out of core — lives in [downstream libraries](/appendix/roadmap/) |

The honest case for using Volt today: you want a stackful coroutine
substrate for Zig on ARM64, you want the synchronous-shape
ergonomics, and you're OK being an early user on Linux (the epoll
and io_uring backends are written but not yet CI-validated) or
willing to wait for the Windows runtime pass.

## Why stackful

The tradeoff: stackful pays ~16 KiB resident per task for "code
looks synchronous." Stackless pays ~hundreds of bytes per task for
"every async function has a different type and the language needs
`async`/`await`."

Zig has no `async`/`await` keyword and won't add one (by maintainer
statement). That removes stackless's main ergonomic argument in this
language. Stackful gives Zig users the synchronous-shape API that
Tokio gives Rust users — without compiling Tokio.

For workloads that genuinely need 1M+ concurrent waiters with tiny
per-task state, stackless is still the right tool. For everything
else — HTTP servers, pipelines, CLIs, network proxies — stackful's
ergonomics dominate. See [Stackful by
design](/architecture/stackful-design/) for the long version.

## Performance — Go as scale reference

Go has been optimised over 15+ years; expecting Volt to beat it
everywhere would be naive. The comparison below exists to know
we're in a sensible range — when Volt is faster it's usually
because Go pays a cost we don't (GC write barriers, function
colouring), not because we out-engineered them. Full receipts in
[Benchmarks](/performance/).

| Workload | Volt | Go | Volt/Go |
|---|---|---|---|
| yield (one-way ctx switch) | 9 ns | 42 ns | 0.21× |
| Mutex contended (8 × 50k) | 15 ns | 81 ns | 0.18× |
| Spsc send+recv (cap=16) | 12 ns | 33 ns | 0.36× |
| TCP echo (64 × 16 RTT × 1 KB) | 8,449 ns | 9,050 ns | 0.93× |
| spawn+wait workers=1 | 101 ns | 136 ns | 0.74× |
| fan-out workers=11 | 117 ns | 107 ns | 1.10× |
| spawn+wait workers=11 (synthetic) | 575 ns | 213 ns | 2.70× |

The single workers=11 outlier is a synthetic spawn-heavy shape
where adding workers can only hurt — there's no parallel work to
amortise the coordination cost. Real-work shapes (fan-out, TCP,
parallel-compute) land at or below the Go reference.
